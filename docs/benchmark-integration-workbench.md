# Benchmark Integration Workbench

## Purpose

`/benchmark-integration/` is a local-only reviewer interface for the typed
Benchmark Result Creation Adapter. It accepts three files:
1. a proposal generated by `scripts/build_benchmark_result_proposal.py`;
2. the separate human Approval Manifest used to create it;
3. the exact raw `data/benchmark-results.json` revision used as the base.

The browser never uploads files or writes to GitHub. It reconstructs the
proposed registry and displays the source/result chain, system and workload
context, five permitted JSON Patch operations, and audit hashes.

## Checks

The browser verifies:
- package schema/type and canonical package SHA256;
- exact match between embedded and separately supplied Approval Manifest;
- Approval Manifest schema, reviewer, explicit decision, review date and
  complete supported result fields;
- exact raw base-registry SHA256 and schema version;
- exactly one existing source with the approved ID;
- exact source snapshot, source class and registered source URL;
- unique result ID and source-scoped source record key;
- deterministic append and reconciliation of source count, registry version,
  import date and summary;
- exact five-operation write set and proposed-registry SHA256;
- audit and policy flags prohibiting evidence promotion, source-truth claims,
  power claims and automatic merge.

All untrusted strings are rendered as text, not HTML. Files are limited to
32 MiB each. Results remain hidden until all checks pass and are cleared on
any failed or incomplete verification.

## Authority and limitations

The browser workbench is a convenience review surface, not the authoritative
validator. It does not execute the complete Python benchmark schema and
semantic validation. The integration workflow must independently rebuild the
package against current master, run `validate_benchmark_results.py`, and
open a review-only PR. The CI validator remains authoritative.

A passing result means only that the package and its constrained database
mutation are internally consistent. It does not authenticate the source,
prove the reported result, establish reproducibility, or make records from
different benchmark suites comparable. Vendor-reported evidence remains
vendor-reported. Missing system/workload context must remain explicit.

## Supported v1 boundary

One result may be appended to one already registered source. This workbench
does not support source creation, updates to existing records, product/model
registry changes, power claims, hardware-counter evidence, runtime traces or
normalized derived metrics. Those require separate typed adapters and
validation paths.
